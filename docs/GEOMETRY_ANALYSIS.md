## 2. 🔴 P0-1. Intersection растягивает события в LINESTRING до 1.3 км

**Файл:** `postgres/init-scripts/08-process-candidates.sql`
**Статус в живой БД:** `ST_ConvexHull PRESENT` (подтверждено через `pg_proc.prosrc`).

### Механизм

Когда у события 3+ кандидатов и пересекаются 2+ пары улиц, CTE `intersections`
накапливает 2+ точки. При `v_true_count > 1`:

```sql
v_geom := ST_ConvexHull(v_true_collected);
```

ConvexHull двух коллинеарных точек — **LINESTRING** между ними (не точка).
Отсюда события, «размазанные» по городу.

### Живые примеры (таблица `events`)

| id | Длина | Текст | Механизм |
|---|---|---|---|
| 33 | **1291 м** | «М. Жукова после Левитана» | 3 кандидата (Жукова, Левитана, ложный «глушко») → 2 точки пересечения 257×390 и 183×257 |
| 126 | 274 м | «по Новосельского между Спиридоновская и Тираспольская» | 3 кандидата → hull |
| 213 | 506 м | «ул.Комсомольская устанавливают камеры» | 3 кандидата, 2 ложных |
| 218 | 136 м | «район МузКомедии + Отрадная, Морская, Уютная, Азарова» | 5 кандидатов |

### Фикс (готов к применению)

```sql
IF v_true_count > 1 THEN
    v_geom := ST_PointOnSurface(ST_ConvexHull(v_true_collected));
END IF;
```

`ST_PointOnSurface` гарантированно возвращает POINT внутри кластера
(на линии — точку на отрезке, на полигоне — внутреннюю точку).

## 3. 🔴 P0-2. Кандидаты matcher'а без поля `type` → pre-filter midpoint мёртв

**Файлы:** `processor/geo_matcher.py`, `processor/semantic_resolver.py`
**Статус:** подтверждено по коду; `PhoneticEntry` (phonetic_index.py) хранит только
`street_id / canonical_name / variant_text` — `type` нет нигде в пайплайне.

### Механизм

1. `_link_span()` возвращает `{geo_id, score, matched_name, text, source}` — без `type`;
2. `_pre_filter()` в `semantic_resolver.py`:
   ```python
   candidate_types = {c.get('type', '') for c in candidates}   # всегда {''}
   ```
   → **Правило 1** («от X до Y» / «между X и Y» → midpoint) и **Правило 2**
   (тип-хинты «село/станция/парк/...») никогда не срабатывают.
3. Ollama в текущей конфигурации отключена → `resolve()` возвращает `None`,
   стратегия = `None` → SQL-авто-определение.

### Последствие (главное открытие)

**28 из 100 событий имеют 2+ матча, но остались `single_match`**, хотя многие —
явные midpoint/intersection:

- «блокпост ❗️ **между Молодая гвардией и Кишинёвска**» → single_match POLYGON
- «блокпост ❗️ **между Молодая и кишенёвской**» → single_match LINESTRING
- «**от** Авангард **в сторону** 2-х Столбов» → single_match POINT
- «Пироговская **угол проспекта Шевченко**» → single_match MULTILINESTRING

Midpoint/intersection сработали только в 11 случаях — авто-путём SQL
(когда улицы реально пересекаются геометрически).

### Фикс (готов к применению)

В `processor/geo_matcher.py`:

```python
# __init__
self._geo_types: Dict[int, str] = {}

# initialize() — после fetch geo_rows (уже есть SELECT id, names, type)
self._geo_types = {row['id']: row['type'] for row in geo_rows if row.get('type')}

# reindex_all() — перестроить карту заодно
# reindex_geo() — SELECT id, names, type ... ; обновить self._geo_types[geo_id]

# _finalize() — перед return добавляем type каждому результату
for r in results:
    r['type'] = self._geo_types.get(r['geo_id'], '')
```

После этого pre-filter Правило 1 начнёт отрабатывать:
«между X и Y» + 2+ кандидата с типами street/market/... → `midpoint`.

## 6. 🟡 P2-2. «X угол Y» / «X / Y» — мягкий сигнал intersection (не гарантия)

«Пироговская угол проспекта Шевченко» — это точно перекрёсток, но событие
остаётся single_match. Пример из экспорта с «/»:
«Малая Арнаутская/ прохоровский сквер три мусора».

### Принцип (по решению пользователя)

Триггер «угол»/«/» — **эвристика с высокой, но не стопроцентной вероятностью**
стратегии `intersection`. Нельзя строго на него полагаться:

1. **Перечисление без триггера** — «X, Y» или «X / Y / Z» тоже указывает на
   пересечение/район. Этот случай уже покрывает авто-путь SQL
   (2+ кандидата → intersection → midpoint → single_match) — триггер лишь
   делает выбор детерминированным и срабатывает там, где геометрии объектов
   не пересекаются, но семантически должны.
2. **Пробелы в gazetteer** — если триггер найден, но объект(ы) не сматчились
   (1 кандидат), intersection недостижим: правило активируется ТОЛЬКО при
   `len(candidates) >= 2` и `type` ∈ street-набору; иначе корректно падает
   на `single_match`.
3. **Недостижимость на этапе геометрии** — если `intersection` выбран, но
   PostGIS не находит пересечений, `process_candidates` уже деградирует
   по цепочке: intersection → midpoint → single_match (стратегия и геометрия
   переписываются). Явная передача `p_strategy='intersection'` не ломает
   этот fallback.

### Фикс (готов к применению, мягкая версия)

```python
# semantic_resolver.py, в _pre_filter, перед return None:

# ── Правило 4 (эвристика): «X угол Y» / «X / Y» → intersection ──
import re as _re
street_types = {'street'}  # расширяется по мере надобности
if len(candidates) >= 2 and any(
        c.get('type') in street_types for c in candidates):
    corner = ('угол' in text_lower or 'углу' in text_lower
              or _re.search(r'(?<!\d)\s*/\s*(?!\d)', text) is not None)
    if corner:
        return {
            'geo_ids': [c['geo_id'] for c in candidates],
            'strategy': 'intersection',
            'reasoning': 'corner_construction_heuristic',
        }
```

⚠️ Slash-триггер guard-ится от цифр (даты «12/06», дроби) через lookarounds.
Решение финальное принимает SQL по фактической геометрии — триггер только
выражает предпочтение.

## 9b. Новая семантика midpoint (по решению пользователя, CAP = 3 км)

Внедрено в midpoint-ветку `process_candidates`:

```sql
-- пары: НЕ пересекаются И 150 м < dist <= 3000 м → midpoint
WHERE a.id < b.id
  AND NOT ST_Intersects(a.geom, b.geom)
  AND ST_Distance(a.geom_m, b.geom_m) > v_pseudo_radius      -- >150 м
  AND ST_Distance(a.geom_m, b.geom_m) <= v_midpoint_max_radius -- <=3000 м
-- при нескольких парах — САМАЯ БЛИЗКАЯ (ORDER BY dist_m LIMIT 1)
-- нет пар в диапазоне → fallback single_match
```

Логика разделения двух понятий:

| Понятие | Диапазон | Где | Семантика |
|---|---|---|---|
| Псевдопересечение | ≤150 м, без пересечения | intersection-ветка | «почти-угол» близких улиц |
| Midpoint | (150 м, 3 км], без пересечения | midpoint-ветка (от/до/между) | «между» разделённых объектов |

Валидация на живых данных:

- Event 70 «между Молодая гвардией и Кишинёвской» (пара 383 м): было fallback
  single_match → теперь **midpoint POINT** ✓ (главный мотивационный кейс).
- Event 126 (пара Спиридонивская×Тираспольская 184 м): midpoint сохраняется ✓.
- Ложные дальние пары (Тенистая×Молдово 88 км, Ильичёвск×Зелёное 108 км,
  Малая Арнаутская×Парканы 101 км): отсекаются CAP'ом → fallback single_match ✓
  (12 событий не ломаются).
- Кограничная пара 635×726 (4 м): midpoint НЕ срабатывает → single_match
  (буква правила «ближе 150 м — не midpoint»).

Известное следствие: события типа «между 9 и 10 Фонтана» (станции вплотную)
перестали быть midpoint → single_match. Соответствует выбранному правилу.

| midpoint | 6 | 1 | **5** |

14 ошибок из 52. Структурные причины:

1. **Метки определяются геометрией, а не языком** (7 из 14 ошибок):
   «по Левитана в сторону круга Жукова» (id 312), «повернули на Бочарова»
   (id 335), «С Палия повернули на Бочарова» — true=intersection ТОЛЬКО
   потому, что улицы пересекаются в данных. Модель не может это угадать
   по тексту — нужен геометрический факт, который SQL уже проверяет.
2. **«Грязные» метки**: id 187 «Пироговская угол Шевченко» — голова ответила
   intersection по явному триггеру «угол», но true=single_match, потому что
   улицы не пересекаются (SQL-фолбэк). Модель «права по языку», метка — нет.
3. **«в сторону X»/«к Y» midpoint** (id 18, 60, 91, 251, 310): фича есть,
   но 13 фичей + 312-dim эмбеддинга не хватает для тонких конструкций.

### 12.4 Рекомендация

1. **Qwen-0.5B для стратегий — нет.** Position bias делает результат
   нестабильным и хуже baseline. Если когда-то подключать LLM — нужна
   модель ≥3B с жёсткой грамматикой (JSON-режим), и только как третий тир.
2. **Голова — рабочий вариант**: +5.8 п.п. над baseline и стабильное
   поведение. Ограничения (п. 12.3) принципиально неустранимы текстовой
   моделью — финальное решение по-прежнему за SQL-цепочкой по геометрии.
3. **Oracle 86.5%** показывает теоретический потолок: ошибки головы и Qwen
   почти не пересекаются (32 кейса, где голова права, а Qwen нет; только
   7 — наоборот). Но «использовать Qwen как дополнительный голос» нельзя
   из-за её position bias — её ответы не информативны.
4. **Практический вывод**: текущая связка (детерминированные правила → SQL
   по геометрии) — оптимальна для масштаба данных (десятки событий/день).
   Голову стоит внедрить только если появится потребность в автономном
   решении для тысяч событий без ручной проверки.

## 13. Решение: SemanticMatcher (rubert-tiny2) отключён полностью

Вопрос пользователя: «отказаться ли от ИИ-моделей или от них есть польза?»
Ответ определён измерением, а не мнением.

### 13.1 Факты из живой системы (2026-08-06)

| Метрика | Значение |
|---|---|
| `semantic_checked_total` (проверок моделью) | **0** |
| Кандидатов в «серой зоне» 0.70–0.85 (право голоса модели) | **1 из 195** |
| Сообщений обработано после пересборки | 36, семантических решений — 0 |
| Цена: инициализация | **+20 сек** (эмбеддинги 2639 алиасов) |
| Цена: вес / RAM | **116 МБ** ONNX / ~290 МБ контейнера |

**Почему серая зона пуста:** цепочка порогов отрезает всё до модели —
stem-тир даёт 0.97 (confident, модель не трогает), typo-тир rapidfuzz
(порог 0.80) в реальности выдаёт кандидатов ≥0.85 («интосане»→Интосана
0.875, «паллпдиума»→Палладиум 0.89, «ромашкавая»→Ромашковая 0.9) — все
проходят как confident мимо модели. Единственный кандидат 0.8
(«паканули»→Парканы) обработан ещё до пересборки.

Итог: SemanticMatcher инициализировался, но **не принимал ни одного
решения**. Чистый убыток без пользы.

### 13.2 Внесённые изменения

1. **`core/settings.py`**: добавлен флаг `SimilarityConfig.semantic_enabled
   = False` (по умолчанию выключено). Комментарии у `surface_typo_threshold`
   и `semantic_accept_threshold` обновлены.
2. **`processor/main.py`**: импорт и создание `SemanticMatcher()` вынесены
   под `if semantic_enabled:` (lazy import). При выключенном флаге модель
   не загружается: `ℹ️ SemanticMatcher disabled (semantic_enabled=False)`.
   `shutdown()` безопасен через `getattr(self, 'semantic_matcher', None)`.
3. **`processor/geo_matcher.py`**: НЕ менялся — `if self._semantic_matcher
   and best_by_geo and text:` ложно при отсутствии подключённого матчера,
   семантический фильтр просто не вызывается.

### 13.3 Что осталось от ИИ и когда вернуть

- **Qwen-0.5B / Ollama**: не подключены (§12.2 — position bias делает их
  непригодными). Не возвращать без модели ≥3B + JSON-грамматики.
- **rubert как эмбеддер**: единственная подтверждённая польза ИИ — обученная
  голова (73.1% vs baseline 67%, §12.1). Возврат = `semantic_enabled=True`
  + скрипт обучения головы. Актуально только при тысячах событий без ручной
  проверки; на текущем масштабе (десятки/день) правила + SQL оптимальны.
- **Файлы модели** (`processor/models/rubert-tiny2-onnx/`, 116 МБ) оставлены
  в репозитории — нужны для будущего re-enable; не грузятся при старте.

### 13.4 Регресс, обнаруженный реплеем, и детерминированный фикс

Реплей 100 сообщений без rubert вскрыл неточность прошлого вывода
«модель не влияла ни на одно решение»: она влияла — редко (1 на ~195
кандидатов), но реально.

**Событие 237 «Станция студенческая прямо на переезде»:**

- Было (с rubert): `random` — семантическая модель ОТКЛОНИЛА ложный
  кандидат «МЕТРО» (surface_typo 0.8, матч по «переезд»). Событие без
  гео-привязки → случайная точка ✓.
- Стало (без rubert): `single_match` (Polygon) — ложный typo-кандидат
  прошёл без валидации → событие привязано к станции МЕТРО, хотя это
  станция «Студенческая» (отсутствует в gazetteer) ✗.

**Почему `semantic_checked_total=0` не показало это:** счётчик обнулился при
пересборке контейнера; в 36 сообщениях нового контейнера не было ни одного
кандидата серой зоны (0.70–0.85) — они редки (1 на ~195). На полном экспорте
100 событий такой кандидат есть — и модель на нём работала.

**Решение (по выбору пользователя): детерминированная защита вместо модели.**
В `process_candidates` для всех single_match-веток (явная `p_strategy`,
`1 совпадение`, Приоритет 3 и защитный fallback) добавлено условие
`v_filtered_scores[1] >= v_score_threshold` (0.85 = geometry_min_score):

```sql
-- 08-process-candidates.sql
IF v_filtered_scores[1] >= v_score_threshold THEN
    -- single_match с геометрией уверенного кандидата
ELSE
    -- слабый лучший кандидат (< 0.85) → random, matches = '[]'
END IF;
```

Логика: single_match-геометрию даёт ТОЛЬКО уверенный кандидат (≥0.85).
Слабые typo-кандидаты 0.80–0.85 без семантического подтверждения НЕ
привязывают событие — событие становится `random`, как если бы модель
отклонила кандидата. Требование согласуется с уже существующим
`geometry_min_score=0.85` (порог для `strong_geoms` в intersection-ветке).

**Проверка на живой БД (SQL применён):**

| Кейс | Вход | Результат |
|---|---|---|
| 237 «Станция студенческая» | [МЕТРО 0.8] | **random** ✓ (было single_match Polygon) |
| Уверенный single_match | [Ядова 0.97] | single_match LINESTRING ✓ |
| 292 (3 кандидата, лучший 0.97) | [0.97, 0.97, 0.8] | single_match, matches=3 ✓ |
| 110 «9 Фонтана возле быка» | [0.97, 0.95] (86 м) | midpoint ✓ |
| 126 «между Спиридоновская и Тираспольская» | [1.0, 0.97, 0.97] | midpoint ✓ |
| Все слабые (0.8, 0.82) | [0.8, 0.82] | **random** ✓ (Приоритет 3 защита) |

**Порог также распространён на явную midpoint-ветку** (`p_strategy='midpoint'`):
`valid_geoms` теперь требует `u.score >= v_score_threshold` (join с
`v_filtered_scores`). Иначе два слабых typo-кандидата (0.80–0.85) дали бы
ложный midpoint — та же дыра, что у события 237, только для midpoint.
Auto-ветка уже была защищена через `strong_geoms`; теперь защита консистентна
во всех ветках. Проверено: (0.97,0.97)→midpoint, (0.8,0.82)→random,
(0.97,0.8)→single_match по уверенному.

**Финальный реплей 100 сообщений (без rubert, с детерминированным фиксом):**

| Стратегия | Эталон (с rubert, §11) | Без rubert + фикс | Δ |
|---|---|---|---|
| single_match | 72 | 71 | −1 |
| random | 14 | **14** | 0 ✓ |
| midpoint | 10 | 11 | +1 |
| intersection | 4 | 4 | 0 ✓ |

Событие 237 вернулось к `random` — регресс закрыт, поведение воспроизводит
модель без её стоимости (+20 сек старта, 116 МБ, ~290 МБ RAM).

Единственное расхождение с эталоном — событие 110 «9 Фонтана возле быка»:
midpoint (11) вместо single_match (10). Это НЕ эффект отключения rubert, а
эффект более раннего фикса «midpoint→auto» (см. §10): пара 9 Фонтана ×
Бернардацци (86 м ≤ 150 м) теперь даёт midpoint через псевдопересечение в
auto-секции. Это УЛУЧШЕНИЕ: текст «между пешеходным переходом и улицей
бернадацци» — явно midpoint, раньше терялся.
