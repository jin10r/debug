# План: интеллектуальный семантический анализатор geo-конфликтов

**Ветка:** `feat/geo-merge-llm-model`
**Статус:** Реализован (v2)
**Дата:** 2026-07-01

---

## 1. Архитектура: модель определяет стратегию → PostGIS вычисляет геометрию

**Центральный принцип:** Модель определяет **стратегию** определения локации на основе семантики текста. В зависимости от стратегии вызываются соответствующие SQL-инструменты PostGIS, которые и вычисляют финальную геометрию.

Размещение компонента: `parser/semantic_resolver.py`

**Назначение:** получает текст сообщения + топ-10 кандидатов от `GeoMatcher`, через Ollama/llama-cpp-python анализирует семантику и возвращает решение: какую стратегию применить и какие geo_ids релевантны.

**Модель НЕ вычисляет геометрию** — только выбирает стратегию (список geo_ids + имя стратегии). PostGIS вычисляет финальную геометрию.

---

## 2. Интерфейс (вход/выход)

**Вход:**
```python
{
  "message_text": "Александровка по дороге в Ильичёвск стоит блокпост",
  "candidates": [
    {"id": 1, "name": "Александровка", "type": "village", "geom_wkt": "..."},
    {"id": 2, "name": "Александровка", "type": "town",    "geom_wkt": "..."},
    {"id": 3, "name": "Александровка", "type": "village", "geom_wkt": "..."},
    {"id": 4, "name": "Ильичёвск",    "type": "town",    "geom_wkt": "..."},
  ]
}
```

**Выход (от модели):**
```python
{
  "geo_ids": [1],           # релевантные кандидаты
  "strategy": "single_match",  # single_match | intersection | midpoint | random
  "reasoning": "Александровка(1) ближе к Ильичёвск(4) чем другие"
}
```

**Модель НЕ возвращает WKT/геометрию.**

---

## 3. Стратегии (SQL-методы PostGIS)

| Стратегия | Когда | SQL |
|---|---|---|
| `single_match` | 1 релевантный объект | **Вернуть полную геометрию объекта** (`geom`) |
| `intersection` | 2+ кандидата, геометрии пересекаются | `ST_Intersection(g1, g2)` |
| `midpoint` | 2+ кандидата **типов** `street`, `market`, `station`, `park`, `landmark` на расстоянии ≤ **150 м** | `ST_LineInterpolatePoint(ST_ShortestLine(...), 0.5)` |
| `random` | ничего не найдено | существующая логика (случайная точка в question_overlay) |

**Важно:** `midpoint` применяется только для указанных типов объектов. Проверка расстояния ≤ 150м — в SQL.

## 5. Требования к модели

- **Вариант A (через Ollama на хосте):** `qwen2.5:0.5b` (уже в конфиге)
- **Вариант B (in-container):** `llama-cpp-python` + Qwen2.5-0.5B GGUF Q4_K_M (~350MB), загружается в `Dockerfile.parser`
- **Температура:** `0` (максимум детерминизма)
- **Prompt:**
  ```
  Ты — анализатор geo-данных. По тексту сообщения и списку кандидатов 
  определи релевантные объекты и выбери стратегию:
  - single_match — один объект
  - intersection — пересечение двух объектов
  - midpoint — средняя точка между 2+ объектами типов street/market/station/park/landmark

  Сообщение: {text}
  Кандидаты: {id, name, type}

  Ответь ТОЛЬКО JSON: {"geo_ids": [...], "strategy": "...", "reasoning": "..."}
  ```
- **Таймаут:** 5–10s, при недоступности → fallback (текущая `process_candidates`)

## 6. Pre-filter быстрых правил (до модели)

Снимает очевидные конфликты без вызова LLM:

1. **Одноимённые объекты разных типов** — если в тексте есть `"село"`, `"пгт"`, `"район"`, `"станция"` → фильтр по типу
2. **Одноимённые объекты** (Александровка ×3) — если в тексте есть второй топоним (Ильичёвск) → выбрать пару с мин. расстоянием
3. **Предложные конструкции** (`"от X до Y"`, `"между X и Y"`) → сразу `midpoint`

Если pre-filter дал однозначное решение → модель не вызывается.

---

## 7. Условия вызова модели

Модель вызывается **только когда**:
- Pre-filter не дал однозначного решения
- `semantic_enabled: True` (в settings)
- Есть конфликт (несколько кандидатов с разными типами/позициями)

**Fallback:** при `semantic_enabled: False`, таймауте или ошибке → используется текущая логика `process_candidates` без модели.

## 10. Контекст принятия решений

### Проблема
GeoMatcher (T1/T2) находит кандидатов, но не может разрешить семантические конфликты:
- Одноимённые объекты разного типа (Александровка — несколько, выбрать ближайшую к Ильичёвску)
- Одноимённые объекты рядом с разными улицами (Сити Центр — псевдопересечение с Жукова)
- Район vs населённый пункт (Таирово — пгт vs район города)
- Направления "от/к", участки между двумя объектами
- Сложные опечатки, не ловящиеся матчером

### Архитектурное решение
- Модель **только анализирует** семантику текста и сопоставляет с кандидатами
- **Не вычисляет** геометрию (чтобы избежать галлюцинаций)
- Вызывает соответствующие SQL-инструменты PostGIS для точного результата
- Компонент **необязательный** — приложение работает без доступа к модели
