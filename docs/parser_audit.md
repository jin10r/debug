# Аудит алгоритма парсера

> Дата: 2026-05-30 · ветка `mawo_parser` · аудит по фактическому коду
> (`parser/*.py` + `postgres/init-scripts/08-process-candidates.sql`).
> **Внимание:** `docs/parser.md` описывает устаревшую архитектуру (natasha NER +
> symspell + navec). В коде её уже нет — действует phonetic-first пайплайн.
> Этот отчёт описывает то, что реально исполняется.

---

## 1. Что делает парсер (фактический пайплайн)

Задача: из шумного русско/украиноязычного текста Telegram-канала извлечь
упоминания улиц Одессы и геолоцировать событие в геометрию PostGIS.

**На сообщение** ([message_processor.py](../parser/message_processor.py)):

```
_extract_text (kurigram Str → plain str, защита от UTF-16 surrogate)
 → strip_tail            (отрезать «сообщить/подписаться»-хвост)
 → preprocess_light      (HTML, таймстампы, UA→RU буквы/суффиксы; регистр сохранён) = preserved → фронтенд
 → _sanitize_text        (выкинуть одиночные суррогаты)
 → strip_emoji           = match_text (только для матчинга)
 → RazdelTokenizer       → tokens
 → Morphology            → lemmas (pymorphy3, LRU 10k)
 → LayerClassifier       → layer (пересечение множеств лемм)
 → [пусто / >380 симв.]  → random point, выход
 → StreetMatcher.find_streets(tokens, lemmas)
 → process_candidates()  (PostGIS: пересечения / псевдо / лучший по score)
 → _insert_event         (один CTE: INSERT + meta + pg_notify)
```

**StreetMatcher** ([street_matcher.py](../parser/street_matcher.py)):

```
_strip_noise            (выкинуть пунктуацию)
_generate_candidates    подряд n-grams 1..max_n(=4) + gap-n-grams (разрыв ≤3)
T2 _phonetic_pass       Metaphone(n-gram) → O(1) lookup → per-word rapidfuzz + multiword-confirm
T3 _lemma_pass          tier-A: exact lemma-tuple;  tier-B: rapidfuzz по ВСЕМ лемма-фразам
merge by street_id      max score, при равенстве phonetic > lemma_exact > lemma_fuzzy
top-K = max_entities(3)
```

**Индекс при старте** ([phonetic_index.py](../parser/phonetic_index.py)): для
каждого alias улицы — словоформы content-токенов (`parse[0].lexeme`, cap 12/слово),
декартово произведение (cap 500/улица), Metaphone каждого варианта → `dict[code]`;
плюс lemma-tuple-индекс и плоский список лемма-фраз для tier-B.

**Масштаб:** 1077 улиц, 141 стоп-слово, ~200–400 ms/сообщение (по docs), один
последовательный воркер.

## 2. Сильные стороны (что менять не нужно)

- **Идемпотентность** через `ON CONFLICT (message_id)` + единый CTE с
  INSERT/meta/notify в одном roundtrip — корректно и эффективно.
- **Атомарный swap индексов** (5 присваиваний без `await`) — реиндексация
  без блокировок и без частичного состояния.
- **LRU-кэш лемматизации** — правильное решение для горячего pymorphy3.
- **`process_candidates`** — геометрия и пересечения целиком в PostGIS одним
  запросом; CROSS JOIN дешёв (k ≤ 3).
- **Очередь producer/consumer** изолирует приём апдейтов от тяжёлой обработки.
- Хорошее покрытие edge-кейсов (surrogate emoji, path-traversal фото,
  auto-reconnect listener).

## 3. Оптимизация

### 3.1 [Hot path] tier-B rapidfuzz сканирует ВСЕ лемма-фразы на каждый кандидат
`_lemma_pass` → `rf_process.extract(lemma_text, grp_phrases, …)` выполняется
для **каждого** не покрытого T2 кандидата по **полному** списку лемма-фраз
(~1000–3000 записей). Кандидатов на сообщение — O(n·max_n + gap-grams),
десятки. Итог: десятки × тысячи сравнений на сообщение — основная стоимость CPU.

Рекомендации (по возрастанию усилий):
1. **Инвертированный индекс по леммам** (`lemma → set[phrase_idx]`): кандидата
   гонять rapidfuzz только против фраз, делящих хотя бы одну лемму/префикс. Режет
   пространство поиска в десятки раз почти без потери recall.
2. **`rapidfuzz.process.cdist`** батчем по всем кандидатам сразу (один SIMD-вызов
   вместо N) вместо `extract` в цикле.
3. Рассмотреть, нужен ли tier-B вообще (см. §4.1) — он самый дорогой и сильнее
   всего пересекается с T2.

### 3.2 [Лёгкая победа] single/multi split фраз пересчитывается на каждый 1-gram
В [street_matcher.py:569-582](../parser/street_matcher.py#L569-L582) для **каждого**
1-gram кандидата заново проходится весь список фраз, чтобы разбить его на
single-word / multi-word группы. Это O(phrases) на каждый 1-gram.
→ Предвычислить два списка (+ их `phrase_meta`) **один раз в `PhoneticIndex.build`**
и отдавать готовыми. Чистая экономия без изменения логики.

### 3.3 [Мёртвый код] `_phonetic_cutoff`
[street_matcher.py:64-78](../parser/street_matcher.py#L64-L78) определена, но
**нигде не вызывается** (порог T2 считает `_score_pair_wise` сам). Удалить —
минус источник путаницы.

### 3.4 Память фонетического индекса
Декартово произведение словоформ (cap 12/слово × cap 500/улица) для 1077 улиц
может давать сотни тысяч вариантов, каждый — отдельная строка + объект
`PhoneticEntry`. `build` логирует `variant_count` — стоит **замерить** на
проде. Если велико: снизить `phonetic_forms_cap`, либо не хранить `variant_text`
в каждой записи (хранить только `street_id`+`canonical`, а `variant_text`
нужен лишь для per-word verify — можно восстанавливать иначе).

### 3.5 Несогласованность пула соединений
[db_adapter.py:46-55](../parser/db_adapter.py#L46-L55) создаёт пул `min=2/max=10`,
а `core.settings.DatabaseConfig` декларирует `pool_min_size=5/max=20` и
`command_timeout=60` (адаптер ставит `30`). Параметры из настроек игнорируются.
→ Читать из `settings.db`, иначе конфиг вводит в заблуждение.

### 3.6 Один последовательный воркер = потолок в 1 ядро
Обработка CPU-bound (pymorphy3 + rapidfuzz + metaphone). При росте потока
канала throughput упрётся в одно ядро. Сейчас приемлемо; на будущее —
`ProcessPoolExecutor` для `find_streets` или несколько воркер-процессов с общей
очередью (порядок не критичен — дедуп по message_id).

## 4. Упрощение пайплайна

Матчер несёт следы длительной эмпирической калибровки: метки R1/R2/R4, G1/G2/G3/G6,
P1/P2, User#1/#2/#3 и **~25 параметров** в `SimilarityConfig`. Это работает, но
порог входа для изменений высокий, а взаимодействие эвристик трудно предсказуемо.

### 4.1 Концептуальная избыточность T2 (phonetic) ↔ T3 tier-B (lemma-fuzzy)
- **T2** строит индекс по *всем словоформам* (инфлексия) и метафонизирует — это
  способ нормализовать падежные окончания + опечатки/транслит.
- **T3 tier-A** (exact lemma-tuple) — нормализует окончания через лемматизацию
  запроса (точно, дёшево, ценно — оставить).
- **T3 tier-B** (rapidfuzz по лемма-фразам) — снова ловит опечатки, но уже над
  леммами.

T2 (метафон+rapidfuzz над инфлектированными формами) и tier-B (rapidfuzz над
леммами) во многом решают одну задачу — устойчивость к опечаткам/вариантам —
разными путями. Кандидат на упрощение: **T2 (phonetic) + T3 tier-A (exact
lemma)**, а дорогой tier-B либо убрать, либо включать только когда оба
предыдущих пусты. Это снимает самый тяжёлый скан (§3.1) и убирает половину
параметров калибровки. Требует прогона на размеченном корпусе для замера
recall до/после.

### 4.2 Многословное подтверждение (User#1) — bonus/penalty
`_confirm_multiword` с окном/порогом/бонусом/штрафом — четыре связанных
параметра, калиброванных вручную (см. длинный комментарий про penalty=15).
Альтернатива: индексировать многословные улицы **только целыми фразами**
(уже почти так в `_generate_variants`) и опираться на gap-n-grams для
разнесённых слов, вместо отдельной bonus/penalty-механики. Снижает число knob'ов.

### 4.3 Вынести калибровку из кода
`length_bias`, `dynamic_threshold_step`, `metaphone_softening`,
`per_word_threshold`, два `*_1gram`-порога — это вес-функции линейной модели,
зашитой в Python. Они уже в `SimilarityConfig`, но логика их применения
размазана по `_score_pair_wise` / `_phonetic_cutoff` / `_lemma_cutoff` /
`_length_bias`. Стоит собрать **scoring в одну функцию** `score(candidate,
entry) -> float` с явной формулой — упростит и тюнинг, и тесты.

### 4.4 Радикальный вариант: перенести матчинг в PostgreSQL
Геометрия уже в Postgres. Расширения `pg_trgm` (триграммная similarity + GIN),
`fuzzystrmatch` (`dmetaphone`, `levenshtein`, `soundex`) и `unaccent`
**не установлены** (есть только postgis/pg_cron/pg_stat_statements). Если их
добавить, alias-матчинг можно выразить SQL-ом: таблица `street_aliases`
(lemma/metaphone-нормализованные), GIN-индекс по trigram, запрос
`ORDER BY similarity(...) DESC LIMIT k`. Тогда исчезают Python-`PhoneticIndex` +
`StreetMatcher` (≈700 + ≈450 строк) и `fonetika`-зависимость, а пересечения
считаются там же, где и геометрия. Минус: теряется тонкая per-word логика и
русская морфология (pg_trgm чисто символьный, dmetaphone слабее на кириллице) —
нужен прогон recall. Сильный кандидат как **долгосрочное** направление.

## 5. Open-source аналоги

Задача = **геопарсинг / toponym resolution**: извлечь топонимы из текста +
резолвить в координаты через справочник (gazetteer) с устойчивостью к
опечаткам и словоформам. Существующие решения:

| Инструмент | Что делает | Применимость здесь |
|---|---|---|
| **Natasha / Slovnet / Yargy** (тот же автор, что razdel/pymorphy) | Русский NER + `AddrExtractor` (правила для улиц/домов) | Прямой аналог «извлечь LOC». В проекте УЖЕ был и убран — стоит зафиксировать, почему phonetic-first победил. |
| **libpostal / pypostal** | Парсинг/нормализация почтовых адресов (обучен на OSM, многоязычный) | Сильно для разбора структурированных адресов; для коротких «упоминаний улицы» в чате избыточно, но нормализация полезна. |
| **Pelias / Photon / Nominatim** | Полноценные геокодеры на OSM + ElasticSearch, fuzzy + phonetic | Если нужен общий геокодер, а не узкий gazetteer Одессы. Тяжёлая инфраструктура. |
| **Mordecai3** | Геопарсинг текста (spaCy NER → GeoNames через ES) | Концептуально ровно эта задача (текст → координаты). Англо-ориентирован. |
| **Elasticsearch/OpenSearch** + russian analyzer + `phonetic` plugin (Beider-Morse/Metaphone) + fuzzy | Индексирует алиасы, запрос `match` с `fuzziness`/phonetic | Может заменить весь рукописный индекс+матчер одним движком. Внешняя зависимость. |
| **PostgreSQL `pg_trgm` + `fuzzystrmatch` + `unaccent`** | Фуззи/фонетика/триграммы прямо в БД | См. §4.4 — самый «родной» путь, геометрия уже в Postgres. |
| **symspellpy / SymSpell** | Symmetric-Delete коррекция опечаток | Был в проекте, убран в пользу Metaphone. |
| **spaCy (ru) / DeepPavlov** | Нейросетевой русский NER | Точнее на «диких» формулировках, но CPU/латентность выше. |
| **flashtext / pyahocorasick** | Сверхбыстрое извлечение ключевых слов (Aho-Corasick) | Точечно для `LayerClassifier` (сейчас пересечение множеств — и так O(1), замена не обязательна). |

**Вывод по аналогам:** проект решает нишевую задачу (фиксированный gazetteer из
~1000 улиц одного города, русский, опечатки/транслит, низкая латентность на CPU
без GPU). Готовый «коробочный» аналог, который точно лёг бы лучше текущего, —
это **(а)** связка `pg_trgm`+`fuzzystrmatch` в уже имеющемся Postgres (минимум
новых зависимостей) либо **(б)** ElasticSearch с phonetic+morphology плагинами
(если гибкости матчинга станет не хватать). Полные геокодеры (Pelias/Nominatim/
Mordecai) — оверкилл для одного города.
