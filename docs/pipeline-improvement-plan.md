## 3. План улучшения пайплайна

### Фаза 0 — Данные справочника (самый дешёвый и большой эффект)

1. **Пополнить geo**: Туристическая (алиас Туристской), Армейская, «Ильфа и Петрова» (единый объект вместо фрагментов), «Жолио-Кюри».
2. **Развернуть сокращения** в алиасах: «пр. Шевченко» → добавить алиасы «проспект Шевченко», «Шевченко» (без префикса). Обработать «ул./пер./пл.», чтобы стем-матч работал без учёта префикса.
3. **G-нейминг сел**: пометить генерные короткие имена (≤6 символов) и села-топонимы, которые могут быть частями названий улиц («Новое», «Петрово»): исключить их из Tier-2 (серой зоны), оставить только точный Tier-1.
4. **Типизация**: «метро» → station/landmark; ревизия 162 коротких имён (источник — `postgres/scripts/enrich_gazetteer_aliases.sql`, дополнить чек-листом).
5. Включить `postgres/tests/test_geo_resolution.sql` в регрессию на новые алиасы.

### Фаза 1 — Матчер (precision/recall)

6. ~~**Двухуличные события (C1)**~~ ✅ **Выполнено (b167f3d)**: anti-list guard меряет дистанцию до геометрии кандидата (не до середины); якоря intersection — реальные точки пересечения пар + ShortestLine-мидпоинты; радиус 40 → 200 м. На живых данных intersection 1% → 22% (23 события), random 22% → 13%.
7. **street_segment (C2)**: по-прежнему 0 срабатываний после фикса перекрёстков (двухуличные уходят в intersection) — рассмотреть удаление как мёртвой гипотезы (меньше SQL-нагрузки) либо ослабить условия.
8. **Tier-2 length-guard (B1)**: diff ≤ max(2, 20%) → рассмотреть max(3, 25%) для имён ≥ 10 символов; зафиксировать политику «Туристическая/Туристская» (вариант местных — считать легитимной опечаткой).
9. **Дефисные имена (B4)**: в `_candidates_sliding_window` склеивать токены вокруг «-» в единый кандидат.
10. **Short-name guard для сел (A1/A2)**: в Tier-2 не матчить village по surface < 7 символов; кандидат «село по обрывку улицы» отклонять, если в том же сообщении есть полноценный стрит-матч.

### Фаза 2 — Confidence и UX

11. **Откалибровать confidence (D)**: exact-матч не обязан быть 1.00 — добавить сигналы: покрытие текста матчами (доля символов), число кандидатов, дистанция до центра зоны. Цель — «1.00» только для однозначных сильных привязок.
12. **Использовать порог 0.7**: в UI помечать события с conf < 0.7 (другая иконка/плашка «привязка приблизительная») — индекс уже есть, добавить флаг в GeoJSON.
13. ~~**Починить подсветку попапов (E1)**~~ ✅ **Выполнено**: фронтенд читает `matched_text` (уже лежал в matches — это лемматизированный surface матчера) с fallback на `matched_part`; тип `matched_text?` добавлен в `geojson.ts`. Проверено e2e: «Посмитного в сторону Генуэзская» → `<strong>Посмитного</strong> в сторону <strong>Генуэзская</strong>».
14. **Убрать опечатку «длиннное»** (B6) и пересмотреть политику длинных сообщений: вместо полного выброса извлекать улицы (длинный текст часто содержит локацию в середине/конце).

### Фаза 3 — Метрики и регрессия

15. **Золотой набор**: собрать 50–100 реальных сообщений с эталонными улицами (пары message_id → эталон; данные для обучения уже копятся в `training_examples`).
16. **Метрики** (скрипт `scripts/analyze_events.py` расширить): recall@k, precision@k, доля random, доля single_match с 2+ matches, доля conf<0.7. Гейт на CI: регресс recall/precision не допускается.
17. **Регрессия**: `test_street_matcher.py` (24 кейса) + новые кейсы из найденных аномалий (A1, A2, B1–B4) как `pytest`-тесты до/после фиксов.
