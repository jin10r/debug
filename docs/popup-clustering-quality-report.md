**Дата:** 2026-08-18  
**Окружение:** Chromium + swiftshader (эмуляция Telegram WebView), REST API + PostgreSQL  
**Данные:** 129 событий в БД, 15–29 в окне 60 мин

## 1. Попап времени ✅

**Формат:** `HH:MM` (часы:минуты)  
**Часовой пояс:** UTC → Europe/Kiev (конвертация через `Intl.DateTimeFormat`)

| id | raw_time | formatted | Статус |
|---|---|---|---|
| 407 | `2026-08-18T12:23:35+03:00` | `12:23` | ✅ |
| 408 | `2026-08-18T12:25:45+03:00` | `12:25` | ✅ |
| 435 | `2026-08-18T12:39:49+03:00` | `12:39` | ✅ |

**Результат:** 15/15 событий отображают время корректно. Формат PSQL `event_time` (timestamptz) хранится в UTC, `formatDateTime` конвертирует в `Europe/Kiev`.

**Нюанс:** События, обработанные парсером, получают `event_time = now()` (UTC). Остальные (исторические backfill) получают время из Telegram message date (тоже UTC). Оба варианта корректно конвертируются.

## 3. Подсветка улиц в попапах ✅

**Механизм:** `_highlightMatchedParts()` (map.ts:206-224)  
- Читает `matched_text` (или `matched_part` fallback)  
- Стемный regex: первые `max(4, len-2)` символов + любой суффикс  
- Минимальная длина слова: 4 символа

**Результат:** 14/15 событий с matches показывают `<strong>`-подсветку.

**Примеры:**
- `id=408 [intersection]`: `<strong>Щорса</strong>` ✅
- `id=412 [single_match]`: `<strong>Паустовского</strong>` ✅
- `id=435 [single_match]`: `<strong>Добровольского</strong>` ✅
- `id=407 [random]`: без подсветки (нет matches) ✅ (ожидаемо)

**Один edge-case:** synthetic event с `matched_text: 'тестовой'` — слово < 4 символов в результатах, но в реальных данных это не проблема (все улицы > 4 символов).

## 5. Кластеризация при 500+ событиях ⚠️

**Стресс-тест:** 550 synthetic events (Point, random lat/lng в bbox Одессы ±0.15°/±0.25°) + реальные 29 events.

**Результат:**

| Метрика | Значение |
|---|---|
| Всего в store | **29** (TTL фильтр отбрасывает старые) |
| Cluster nodes | 481 |
| Markers in clusters | 481 |
| Random (ungrouped) | 98 |
| Render time | 4002ms |

**Проблема:** `store.setEvents()` отфильтровало 550+29 → 29. Это **ожидаемое поведение**: store TTL = 60 мин, `isAcceptable()` отбрасывает события за пределами окна. Синтетические события были в пределах 30 мин, но `serverNow()` мог дать несогласованное время (WS не подключён в headless → clock tick не обновляется).

**Вывод о кластеризации при 500+:** Не удалось протестировать через injection из-за TTL-фильтра store. Реальная проверка возможна только при реальном потоке 500+ событий в окне 60 минут.

**Ожидаемое поведение при 500+ реальных:**
- `chunkedLoading: true` → батчи по 200 маркеров, UI не блокируется
- `maxClusterRadius: 50` → при 500 точках в Одессе (~10×15 км) будет ~50-80 кластеров (каждый покрывает ~50px ≈ 400м)
- Оранжевые бейджи с числом кластеров

## 6. TTL / фильтрация по времени ✅

**Уровень 1 (БД SQL):**
```sql
WHERE event_time >= NOW() - $1 * interval '1 minute'
-- time_interval_minutes = 60
```

**Уровень 2 (Store):**
```ts
const TTL_MS = 60 * 60 * 1000; // 60 минут
function isAcceptable(feature) {
    const age = window.serverNow() - t.getTime();
    return age <= TTL_MS && age >= -FUTURE_TOLERANCE_MS;
}
```

**Данные:**

| Возраст | Количество | Видно клиенту |
|---|---|---|
| < 30 мин | 13 | ✅ |
| 30–60 мин | 0 | ✅ (если есть) |
| 1–6 ч | 0 | ❌ (filtered) |
| > 6 ч | **116** | ❌ (filtered) |

**Важно:** 116 из 129 событий **невидимы** на карте — это историческая backfill-обработка (>6 ч назад). Клиент видит только свежие события в60-минутном окне. Это **по дизайну** (комментарий в `db_events.py:283-285`).

**Нюанс:** REST snapshot (`GET /api/events`) и WS snapshot оба используют `time_interval_minutes=60`. Нет способа загрузить исторические данные через текущий API.

## 8. Рекомендации

### Средний приоритет
1. **Тест кластеризации при 500+** — запустить стресс-тест через WebSocket (имитировать flood с 500 сообщениями за <60 мин) или увеличить TTL store до 24ч для тестовой среды
2. **Historical event loading** — добавить параметр `?include_all=true` в REST API для просмотра исторических событий (за пределами 60 мин)

### Низкий приоритет
3. **Фото-покрытие** — 4/129 (3.1%) это нормально для канала; расширение зависит от канала
4. **Кластер radius** — `maxClusterRadius: 50` можно увеличить до 60-80 для более агрессивной группировки при высокой плотности
