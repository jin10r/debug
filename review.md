🔍 Полный обзор проекта Survival Map
1. Общее резюме
Проект — Telegram Mini App «карта событий Одессы»: parser (kurigram) → processor (NLP-пайплайн + PostGIS) → core (aiohttp REST/WS) → web (nginx). Пять сервисов в Docker Compose, события живут 60 минут, доставка через WebSocket.
Сильные стороны (их много, это важно отметить):
- Грамотная архитектура: изолированная сеть БД ( internal: true ), LISTEN/NOTIFY вместо поллинга, очередь  pending_events  с  SKIP LOCKED , часовое партиционирование  events  с  DROP TABLE  вместо DELETE.
- Отличная инженерная культура: подробные русскоязычные комментарии, осознанные компромиссы (в каждом решении видно «почему»), graceful shutdown, retry с backoff, circuit breaker, адаптивный воркер-пул с backpressure.
- Защита от path traversal в медиа, constant-time сравнение подписей, строгий CSP на nginx, rate-limit на edge и в приложении.
- Продуманный инкрементный рендер фронтенда (diff по  renderedById ), LRU-кэши лемматизации, оффлайн-режим PWA.
Главная проблема — тесты и CI красные, часть эндпоинтов молча сломана. Детали ниже.

2. 🔴 Критические проблемы (нужно чинить в первую очередь)
2.1 Тестовый прогон не стартует, CI падает
 tests/test_text_preprocessor.py  загружает  parser/text_preprocessor.py , которого больше нет — модуль переехал в  core/text_preprocessor.py . Ошибка сбора прерывает весь прогон ( pytest  умирает на collection). Плюс ~16 падающих тестов:
-  test_semantic_resolver.py  — тесты описывают поведение старого резолвера (type-hints «село/парк/станция», дубликаты имён), которое упрощённый  SemanticResolver  больше не реализует;
-  test_webview_validation.py  и  test_telegram_validation.py  — проверяют старое поведение  validate-init  (dev-mode, формат ошибок);
-  test_valid_init_data  — падает.
То есть  .gitlab-ci.yml  (шаг  pytest -q ) всегда красный, и ни один регресс не ловится.
Рекомендации: обновить пути загрузки модулей в  tests/conftest.py  ( load_module_by_path ), переписать устаревшие тесты под актуальный контракт, добиться зелёного пайплайна, добавить  pytest-asyncio  в  requirements-dev.txt  (сейчас  asyncio_mode = auto  в  pytest.ini , но плагин не установлен — предупреждение при сборе).
2.2  /metrics  падает с AttributeError
 core/utils/metrics.py:280  вызывает  request.app['db_pool'].get_pool_stats()  — такого метода у класса  Database  (core/db/db_base.py) нет. Любой запрос к  /metrics  → 500. Сами метрики Prometheus определены, но endpoint сломан.
Рекомендация: заменить на реальные  pool.get_size() / get_idle_size() / get_max_size()  (как уже сделано в  health_detailed ).
2.3 Запросы к несуществующей таблице  table_updates 
-  core/db/db_events.py:158  ( get_latest_update_time ) и  core/db/db_geo.py:32  —  SELECT last_updated FROM table_updates , но такой таблицы нет в схеме (02-tables.sql).
- Следствие:  /api/data_status  ( get_data_status_handler ) всегда молча возвращает  no_data  или 500 — «данные не обновляются» даже когда всё работает.
Рекомендация: переписать на  events_meta.updated_at  /  MAX(event_time)  либо удалить legacy-методы.
2.4 Мёртвый код, ссылающийся на несуществующую SQL-функцию
 db_events.add_event()  и  dbconnect.call_process_event()  вызывают  SELECT * FROM process_event(...)  — такой функции нет ни в одном init-скрипте. Код не используется (конвейер идёт через processor), но остаётся ловушкой.
Рекомендация: удалить legacy-ветки  Request.add_event ,  call_process_event ,  EventOperations.add_event  и связанный с ними код.

3. 🟠 Архитектура и качество кода
3.1 Дублирование DBAdapter
 parser/db_adapter.py  и  processor/db_adapter.py  — почти побайтово одинаковые классы (md5 различается минимально). Плюс третий вариант в  core/db/db_base.py .
Рекомендация: один общий модуль (например,  core/db/db_base.py  уже есть) — оставить единый  asyncpg.create_pool  фабрику.
3.2 Схема «конфиг в dataclass» — хорошо, но с изъянами
Жёсткие дефолты в  core/settings.py  вместо env — осознанный выбор, документирован. Но:
-  ENTITY_SIMILARITY_THRESHOLD  упомянут в  env.example , но не читается в  load_settings  — переменная-фантом.
-  DatabaseConfig  настраивает  pool_max_size=30 , при этом роль  core  в БД имеет только SELECT, а код пытается писать — несогласованность ролевой модели.
3.3 Несогласованность версий и здоровья
-  /health/detailed  отдаёт  version: '1.0.6' , а  set_application_info(version='2.0.0')  — другие данные.
-  cache._connected  всегда  False  (in-memory кэш) → health всегда «degraded». Честнее убрать поле из проверки.
3.4 Мёртвый/недоделанный функционал
- Materialized views ( 12-materialized-views.sql ) определены и обновляются pg_cron каждые 30с, но нигде не используются в коде ( db_events  читает  events  напрямую). Накладные расходы на REFRESH без пользы — либо задействовать в API, либо удалить.
-  postgres/config/queries.yml  — конфиг для  postgres_exporter , но самого сервиса в compose нет. Мёртвый конфиг.
-  PARSER_STATEMENT_TIMEOUT  /  CORE_STATEMENT_TIMEOUT  в compose передаются в postgres, но init-скрипт  05-role-timeouts.sql  хардкодит таймауты — переменные не читаются.
- Неиспользуемые хелперы метрик ( record_cache_hit ,  record_slow_query ) — нигде не вызываются.
-  SpatialOperations  ( get_batch_intersections ,  get_max_distance_in_polygon  и др.) — используются ли реально? Поиск показывает только legacy-прокси в  dbconnect .
3.5 Документация
- README.md удалён из рабочего дерева — репозиторий без главного документа. Ветка «ahead of origin» с кучей незакоммиченных изменений, включая удаление всех  docs/*.md .
-  .kiro/  (с  specs/ ) не покрыт  .gitignore  (там записан  .kilo/  — опечатка).

5. 🟢 Производительность и оптимизация
Уже оптимизировано (не трогать)
- Часовые партиции + BRIN-индекс для time-series скан-ов;
- LISTEN/NOTIFY вместо поллинга для WS-доставки и фото;
- LRU-кэши морфологии (20K лемм, 20K стемов), JWT-верификации (10K/10с);
- Инкрементный рендер карты, TTL-кэш GeoJSON (30–60с) + ETag;
- Адаптивный воркер-пул парсера, circuit breaker процессора,  ThreadPoolExecutor  для rapidfuzz.
Возможности для улучшения
1. Idle-нагрузка процессора: 5 воркеров ×  _fetch_pending  каждые 0.5с = ~10 SELECT/сек даже при пустой очереди. Лучше: один LISTEN/NOTIFY на  pending_events  (триггер  NOTIFY  при INSERT) + фолбэк-poll раз в 5–10с.
2. WS-broadcast:  SEND_TIMEOUT=5s  — один зависший клиент задерживает рассылку всем (gather ждёт). Рассмотреть параллельную отправку с ранним выходом или стриминг. Плюс  heartbeat=120  — медленное обнаружение мёртвых соединений; 30с в коде cleanup-задачи несогласован с 120с у aiohttp.
3. In-memory кэш — осознанное ограничение: при масштабировании core на >1 процесса кэш разойдётся и TTL-инвалидация перестанет работать. Для прода — Redis (1 контейнер) или смириться с single-replica.
4.  /api/events  POST + кэш: кэш-ключ учитывает  time_filter  и слои, но не  since /инкрементальные запросы — с кэшем они не смешиваются (BYPASS) — ок. Хорошо.
5. Geo-кэш 1 час — при обновлении  geo  (reindex через NOTIFY) кэш не инвалидируется. Подписываться на  geo_updated  в core или уменьшить TTL.
6. Dockerfile.core:  libpq-dev  не нужен для asyncpg (чистый Python) — можно убрать, уменьшив образ.

6. 🟣 Фронтенд
- Хорошая реактивная архитектура: zustand store — единственный источник правды,  event_manager  подписан на store,  local_cache  — только адаптер персистентности. Отсутствие алиасинга — плюс.
- Инкрементный рендер (diff  renderedById ) — правильно; hard-cap 5000 событий — разумная страховка.
- WebSocket с heartbeat 25с/15с, jitter-реконнектом, «само-лечением» по visibility/online — выше среднего качества.
- Замечания:
-  console.log  на каждом действии в проде (store, WS) — шумно; обернуть в debug-флаг;
- nginx  /js/  rewrite-каскад для  __v__/TOKEN  URL — хрупкая legacy-схема, в sw.js precache уже идёт  /dist/ ; стоит оставить один путь (webpack dist);
-  TILE_PROVIDERS  хардкод сторонних тайловых серверов (openfreemap, OSM) — для прода желателен свой/кешируемый источник;
-  formatDateTime  парсит время как  HH:MM  из ISO-строки без учёта часового пояса — при  T14:30:00+00:00  покажет 14:30 вместо 17:30 (Киев). Проверить — в properties  time  приходит с  +00:00  из  _INSERT_EVENT_* .
